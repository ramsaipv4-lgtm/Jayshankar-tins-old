# Prompt: GENERATE-INTERVIEW-PREP (first-principles reimplementation drills from a finished project)

> **The prompt you paste into a fresh LLM session when a finished TINS project should
> yield technical-interview practice** — one guided, from-scratch reimplementation
> exercise per core CS/systems concept the project's own real stack actually touches,
> sourced from what this project really does rather than a generic interview-prep list.
> It produces a sibling folder, `<project>-curriculum/interview-prep/`, generated one
> file at a time so each exercise gets full, unhurried, maximally descriptive treatment.
>
> **Run this with a frontier model at extended/max thinking.** Designing a from-scratch
> reimplementation exercise — one that isolates a real concept cleanly, poses it at the
> right difficulty, and works out a correct reference solution the exercise can be
> checked against — is itself a hard design task, not a summarization task. The kit
> already has a precedent for this exact recommendation: `scripts/check-task-independence.mjs`
> (D29) recommends escalating merge-conflict judgment calls to "a senior engineer or a
> frontier model at extended/max thinking" when the judgment is genuinely hard to get
> right cheaply. The same reasoning applies here, more so — this prompt is asked to
> invent well-posed exercises, not just judge existing ones. A weaker or budget model can
> still run this prompt, but expect thinner exercises and shakier reference solutions;
> tell the user this trade-off plainly if you know your own capability tier is not a
> frontier one.
>
> **Companion to `prompts/GENERATE-CURRICULUM.md`.** Run that prompt first — this one
> reads the curriculum it produces (`00-START-HERE.md`, `GLOSSARY.md`,
> `CONCEPT-TO-CODE-INDEX.md`, the per-module `README.md`s) as its own source material,
> on top of the project's original artifacts. This is a separate, optional pass: run it
> only when interview-prep specifically is wanted, never automatically chained on after
> `GENERATE-CURRICULUM.md` finishes.
>
> **Source:** D31 (session 15). Reuses `scripts/private-to-public.mjs` (D30) as-is for
> the safety gate — no new scanner, no new banned-terms list.
>
> The kit must already be vendored at `./tins-kit/`, and `../<project-name>-curriculum/`
> must already exist (from a prior `GENERATE-CURRICULUM.md` run). This prompt operates on
> the private working copy and the curriculum folder for source material, and writes its
> output into `../<project-name>-curriculum/interview-prep/` — never inside the private
> copy, never inside the D30 public repo.

---

## When to use

You (an LLM session) have a finished TINS project with a curriculum already generated by
`prompts/GENERATE-CURRICULUM.md`, and the user specifically wants interview-prep material
from it: practice for OpenAI/Anthropic-style technical interviews (system design,
first-principles implementation, debugging under pressure) built from concepts this real
project actually exercises, not a generic algorithms-interview question bank. Run this in
a **fresh session**, ideally on a frontier model at extended/max thinking (see above). It
works entirely from the project's and curriculum's real artifacts, never from memory of
the session that originally built the project — if a fresh session reading those
artifacts can't produce a well-posed exercise for some concept, that's a sign the concept
needs clearer treatment in the curriculum itself, worth fixing upstream in
`GENERATE-CURRICULUM.md`'s output rather than a reason to route around fresh-session
discipline.

---

## The prompt

```
You are turning a finished TINS project's real working history into first-principles
technical-interview practice. Your working directory is $PWD, the private working copy.
The project has the kit vendored at ./tins-kit/, and a curriculum already exists at
../<project-name>-curriculum/ (from a prior GENERATE-CURRICULUM.md run). Your job is to
produce ../<project-name>-curriculum/interview-prep/, containing an overview and one
guided from-scratch reimplementation exercise per core CS/systems concept this project's
REAL stack actually touches — never a generic list of textbook CS topics unrelated to
what this project does.

If you are not running as a frontier model with extended/max thinking enabled, tell the
user now: exercise quality and reference-solution correctness will be weaker than this
prompt is designed for, and offer to continue anyway or have them re-run this prompt in
a stronger session.

You will generate this ONE FILE PER TURN. Do not compress multiple exercises into a
single response to save turns — the whole point of this pacing is to give each exercise
full, unhurried, maximally descriptive treatment, including a worked reference solution
you have actually reasoned through, not sketched. Stop after each file and wait for the
user (or your own next turn, if you are continuing unattended) before starting the next
one.

---

## The 9 steps (do them in this order)

### Step 0 — Confirm your location and prerequisites

```bash
pwd
ls -la
ls tins-kit/                                              # confirm the kit is here
ls ../<project-name>-curriculum/                           # confirm the curriculum exists
node tins-kit/scripts/validate.mjs --spec=SPEC.md           # should be green
node --test tins-kit/scripts/selftest.mjs                   # should be green
```

If `../<project-name>-curriculum/` doesn't exist yet, tell the user to run
`prompts/GENERATE-CURRICULUM.md` first and stop — this prompt reads that curriculum's
concept breakdown as its own source material and has nothing to build from without it.
If the gate isn't green, tell the user and stop, for the same reason
`GENERATE-CURRICULUM.md` does: exercises built from an unfinished, inconsistent project
teach the wrong lessons.

### Step 1 — Check for an in-progress run (resume, don't restart)

```bash
cat ../<project-name>-curriculum/interview-prep/CURRICULUM-PROGRESS.md 2>/dev/null
```

If this file already exists and has entries marked pending, this is a resume: skip
straight to Step 6 and continue from the first pending file in manifest order. Do NOT
regenerate files already marked done. Only start fresh at Step 2 if there's no existing
progress file for this interview-prep run, or the user explicitly asks for a full
regeneration. (This is a separate progress file from `GENERATE-CURRICULUM.md`'s own
`../<project-name>-curriculum/CURRICULUM-PROGRESS.md` — don't confuse or merge the two.)

### Step 2 — Read the real source material

| # | File | Why |
|---|---|---|
| 1 | `../<project-name>-curriculum/CONCEPT-TO-CODE-INDEX.md` | The already-derived map of concept → real implementation — the starting point for deciding which concepts are substantial enough to earn a reimplementation exercise |
| 2 | `../<project-name>-curriculum/GLOSSARY.md` and `00-START-HERE.md` | Confirms terminology and the prerequisite map, so exercises assume exactly what the curriculum already established, no more and no less |
| 3 | `../<project-name>-curriculum/modules/*/README.md` | The real "how it works" explanations each exercise's reference solution needs to be consistent with |
| 4 | `SPEC.md` §2 (functionality) and §7 (error handling) | The real requirements a faithful reimplementation exercise should hold itself to |
| 5 | The code itself | Ground truth for how the real implementation actually solved the problem, used to build and sanity-check your own reference solution |

### Step 3 — Identify the core CS/systems concepts worth an exercise

From the concept-to-code index and module READMEs, list the concepts that are (a) a real,
substantial piece of engineering judgment in this project — not boilerplate — and (b)
recognizable as a standard CS/systems topic an interviewer could plausibly probe (parsing
and validation, state machines, concurrency and race conditions, caching and eviction,
graph traversal, retry/backoff and idempotency, schema/data-modeling trade-offs,
algorithmic complexity choices, and so on — whatever this project's stack actually
surfaces, not this example list). Drop concepts that are real but too thin to sustain a
standalone reimplementation exercise; note in the manifest, briefly, why each dropped
concept was left out, so the omission reads as a decision rather than an oversight.

### Step 4 — For each concept, design one exercise and work out its reference solution

For each concept from Step 3, before writing the exercise file:
1. Decide the exercise's scope — small enough to attempt from scratch in an
   interview-length session (think 30-60 minutes of focused work), faithful enough to the
   real project's version that solving it teaches the real thing.
2. Actually work out a correct reference solution yourself. Do not sketch a plausible-
   looking approach and defer verification to the reader — reason it through, check edge
   cases against the project's own real §7 error-handling table where relevant, and be
   prepared to show your work.
3. Note where the exercise's clean version diverges from the real project's version (the
   real code may have extra complexity from constraints the exercise deliberately
   simplifies away) and plan to say so explicitly in the file, so a learner who later
   reads the real code isn't confused by the gap.

### Step 5 — Write the manifest and initialize the progress file

Create `../<project-name>-curriculum/interview-prep/` and write
`CURRICULUM-PROGRESS.md` inside it (start from `tins-kit/templates/CURRICULUM-PROGRESS.md`)
listing every file this run will produce, in the order you'll generate them, each marked
`pending`:

```
00-OVERVIEW.md
01-<concept-slug>.md
02-<concept-slug>.md
...
```

Show this manifest to the user (or state it plainly if running unattended) before
generating anything, including the brief note on any concepts you deliberately dropped in
Step 3, so they know what's coming and why the list is what it is.

### Step 6 — Generate files, one per turn, in manifest order

For each file in the manifest, in order:

1. Write the file in full — see "Content rules" below for what each file needs. Be as
   descriptive as the file warrants, including the full worked reference solution from
   Step 4; this pacing exists specifically so you are not compressing content to fit a
   turn budget.
2. Update `CURRICULUM-PROGRESS.md`: mark this file `done`.
3. Stop. Do not start the next file in the same turn. If running interactively, a short
   note ("`01-<concept-slug>.md` is done — reply to continue with the next exercise") is
   enough; don't pad it into a full response. If running unattended across scheduled
   turns, proceed to the next file on your next turn.

### Step 7 — Run the safety gate

Once every file in the manifest is `done`:

```bash
node tins-kit/scripts/private-to-public.mjs ../<project-name>-curriculum/ --scan-only
```

This re-scans the whole curriculum sibling folder, including the new `interview-prep/`
subfolder, reusing D30's scanner exactly as-is — same banned-terms list, same two
categories (methodology fingerprints, LLM-authorship fingerprints). No new script, no new
list.

### Step 8 — Fix any leaks, re-scan until clean, then report completion

If Step 7 exits non-zero, fix the flagged file(s) directly (freshly authored, not copied
from anywhere — there's no "source" to fix instead) and re-run Step 7 until it exits 0.
Then tell the user: how many exercises, which concepts were covered, which were
deliberately dropped and why, and remind them each exercise's reference solution is meant
to be checked against, not read before attempting the exercise.

---

## Content rules (apply to every file you write)

**Voice: direct, second-person, instructional — not corporate, not an AI assistant's
voice.** Same rule as `GENERATE-CURRICULUM.md` — see that prompt's content rules and
`lib/patterns/private-to-public.md` §3.0 for the full rationale. First-person LLM voice,
meta-commentary about the writing process, and stock assistant openers/closers are wrong
here exactly as they are there.

**Everything traces to something real.** The concept must be real (traced to the
concept-to-code index or the code itself); the exercise's simplifications and any
constructed example data must be labeled as such, not presented as if they came from the
project's own history.

**`00-OVERVIEW.md`** — what this folder is for (technical-interview practice, not a
continuation of the curriculum's own teaching sequence), how to use it (attempt an
exercise cold, using only its problem statement, before reading its reference solution),
the list of concepts covered with a one-line description of what each drills, and the
list of concepts deliberately left out with the reason. Recommend a stated time-box per
exercise (interview-length, not take-home-length) so practice stays realistic.

**`NN-<concept-slug>.md`** — each exercise file, structured in this order so a reader can
stop reading before the answer:
1. **Problem statement.** The concept, framed as a from-scratch build task, with concrete
   inputs/outputs/constraints — written the way an interviewer would actually pose it,
   not as a textbook definition.
2. **Constraints and what "correct" means here** — the edge cases a real answer needs to
   handle, drawn from the project's own real `SPEC.md` §7 error-handling table where the
   concept maps to one.
3. A clear divider (e.g. "--- Stop here and attempt it yourself before reading on ---").
4. **Walkthrough of a correct approach** — the reasoning process, not just the answer:
   what the right first question to ask is, what the naive approach gets wrong, how to
   get from naive to correct.
5. **Worked reference solution** — real, complete, reasoned-through code or pseudocode
   (whichever fits the concept), checked against the constraints from point 2.
6. **How this differs from the real project's version**, and why the real version is more
   (or differently) complex — pointing to the real module/file via
   `../<project-name>-curriculum/CONCEPT-TO-CODE-INDEX.md` or the code directly.

---

## What you do NOT do

- **Generate more than one file per turn.** Same discipline as `GENERATE-CURRICULUM.md`,
  for the same reason.
- **Invent a concept the project's real stack doesn't actually touch**, just to round out
  a "standard" interview-topics list. Every exercise must trace to the concept-to-code
  index or the code itself.
- **Publish a reference solution you have not actually reasoned through.** A plausible-
  looking but wrong reference solution is worse than no exercise at all.
- **Write in D30's corporate product voice or in first-person LLM voice.** Same rule as
  `GENERATE-CURRICULUM.md`.
- **Skip the safety gate.** Same reasoning as `GENERATE-CURRICULUM.md` — interview-prep
  content can leak the same fingerprints the product repo and the rest of the curriculum
  can.
- **Chain automatically off the end of a `GENERATE-CURRICULUM.md` run.** This is a
  separate, optional pass, run only when specifically wanted.
- **Regenerate files already marked `done`** in this folder's own progress file, on a
  resumed run.

---

## What success looks like

1. The user has a finished curriculum (from `GENERATE-CURRICULUM.md`) and specifically
   wants interview-prep material from it.
2. Ideally, you are a frontier model at extended/max thinking; if not, you've said so
   plainly (Step 0).
3. You confirm the curriculum exists and the gate is green (Step 0), and resume an
   in-progress run if one exists (Step 1).
4. You read the real source material (Step 2), identify the project's real core
   CS/systems concepts (Step 3), and design and actually work out a correct reference
   solution for each before writing anything (Step 4).
5. You write and show the manifest, including what you deliberately dropped and why,
   before generating anything (Step 5).
6. You generate one file per turn, each maximally descriptive, each with a real
   worked-through reference solution, in the right instructional voice (Step 6).
7. You run the safety gate and fix anything it finds, then report completion (Steps 7-8).
8. A learner can attempt `01-<concept-slug>.md` cold, in something like interview
   conditions, then check their approach against a reference solution that actually holds
   up.

Begin with Step 0.
```
