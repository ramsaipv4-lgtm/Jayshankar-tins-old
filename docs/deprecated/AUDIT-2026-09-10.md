## 2. The validator regression — root cause and fix

**Status: FIXED in this session** (verify by re-running `npm run validate` / `npm run selftest`
yourself — see §1's commands).

**Root cause.** `scripts/validate.mjs`'s `§8.1a` check (function `runKitChecks`, explicitly
labeled `// Part A — Kit's structural checks (re-implemented)`) is meant to mirror
`tins-kit/scripts/validate.mjs`'s own `§8.1a` check verbatim — both check for a canonical marker
at the top of the spec file. The kit's real convention (confirmed against
`tins-kit/scripts/validate.mjs` line 197 and `tins-kit/templates/SPEC.md` line 1) is:

```
<!-- TINS Specification v1.0 -->
```

At some point, Jayshankar's `scripts/validate.mjs` had this literal string changed to
`<!-- Jayshankar Specification v1.0 -->` — a one-project-only marker that was never added to
`SPEC.md` itself (SPEC.md's header has read `<!-- TINS Specification v1.0 -->` unchanged since
W1, 2026-08-05, and no `BUILDER-DECISIONS-REVIEW.md` entry documents ever intending to add a
project-specific marker). File-mtime evidence: `scripts/validate.mjs` was last modified
2026-08-14 07:56 — **after** `HANDOVER.md`'s last save at 2026-08-14 04:51, which is the save
that claimed "72/72 green." So this edit landed post-hoc, undocumented, and has been silently
broken for roughly four weeks as of this audit — in direct violation of the project's own rule
("never let a validator failure through" / "an unrecorded finding is a finding the next session
pays for again").

**Fix applied.** Reverted `scripts/validate.mjs`'s `§8.1a` check back to require
`<!-- TINS Specification v1.0 -->`, matching both `SPEC.md`'s actual content and the kit's own
convention. The same drift had also touched `scripts/selftest.mjs`'s `defectNoSpecMarker()`
helper (it stripped the wrong marker string, so its own regression test silently stopped
testing anything) — fixed that too. Logged as a new numbered decision in
`BUILDER-DECISIONS-REVIEW.md`. Confirmed both green: `npm run validate` → 72 pass, 0 warn, 0
fail; `npm run selftest` → 9/9 pass.

## 3. Everything else found in this audit (condensed — full detail was given to the user in chat)

(delivery/sale/transfer/spoilage), audit log viewer, PWA offline banner, RLS on all 9 tables,
deterministic idempotent seed. Documented, honest limitations: no race-condition locking on
sale/spoilage FIFO (only transfer got `SELECT ... FOR UPDATE`, migration `0005`); sales
exceeding the oldest batch report a "shortfall" instead of cascading; no admin CRUD UI for
vendors/SKUs/locations; no phone-OTP auth; no offline write-queue (read-only when offline, by
design).

between "2 locations in V1" (D9) and the seed/acceptance tests requiring a 3rd (`freezer`)
location; no specified mechanism for promoting a user to admin despite the spec requiring one;
an acknowledged gap in how a sale correction reconciles against the immutable audit log; a FIFO
tiebreak (`id ASC`) required by an acceptance criterion but absent from the actual algorithm SQL.
